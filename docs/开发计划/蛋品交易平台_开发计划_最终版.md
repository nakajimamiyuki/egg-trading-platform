## 1. 项目概述

面向鸡蛋产业链的 B2B 交易平台，含 **养殖端、客户端、业务端、财务端** 四个业务端口 + 一组基础模块。核心业务为"交割仓 + 平台垫资"模式，支持三种销售模式：

- **模式①** 蛋库出库标准模式：客户付 20% 定金 → 平台垫 80% → 现场装车核验 → 三方确认出库单 → 客户付 80% 尾款 → 平台付 20% 尾款 → 扫码核销放行
- **模式②** 在途货物预付模式：远端客户，平台叫车（运满满），养殖户收齐 100% 全款才放行，GPS 在途追踪
- **模式③** 渠道账期服务模式：渠道客户（如京东 60 天账期），风控尽调前置，尾款内扣平台分利（如 1 元/件）

| 口径 | 工期 |

### 最耗时的 5 件事（关键路径）

1. **需求字段级确认** — 需求清单只到功能点级，字段和业务规则需业务方确认，是总工期最大变量
2. **三种销售模式的资金状态机** — 垫资/尾款/分利内扣/退款/折价，占总开发量约 30%
3. **第三方接口商务与联调** — 银企直联（1–3 个月）、电子签、支付商户号等，外部流程无法压缩
4. **库存并发与扫码核销** — "扫码是放行唯一凭证"，需幂等 + 分布式锁 + 专项压测
5. **里程碑审查轮次** — 6 个里程碑，每轮验收控制在 1 小时内

## 3. 技术架构与部署

### 3.1 技术栈（按既有设计文档）

- 后端：Python 3.12 + FastAPI + SQLAlchemy 2.0 + Pydantic V2 + Alembic
- 前端：Vue3 + TypeScript + Vite + Pinia + Vue Router + Element Plus + ECharts
- 数据：PostgreSQL 15 + Redis 7 + RabbitMQ + MinIO
- 部署：Docker / Docker Compose（本地）→ Kubernetes（云上生产）

### 3.2 本地 Docker 架构（开发与前 5 个里程碑的全部环境）

```
┌─────────────────────────────────────────────┐
│              本机 (Docker Desktop)            │
│                                              │
│  ┌─────────┐   ┌──────────────────────────┐ │
│  │  nginx  │──▶│  frontend (Vue3 构建产物)  │ │
│  │  :80    │   └──────────────────────────┘ │
│  │         │──▶│  backend (FastAPI+uvicorn)│ │
│  └─────────┘   └──────────────────────────┘ │
│                        │                     │
│  ┌────────┐ ┌───────┐ ┌▼───────┐ ┌───────┐  │
│  │postgres│ │ redis │ │rabbitmq│ │ minio │  │
│  │  :5432 │ │ :6379 │ │ :5672  │ │ :9000 │  │
│  └────────┘ └───────┘ └────────┘ └───────┘  │
└─────────────────────────────────────────────┘
```

- 一条 `docker compose up -d` 拉起全部服务，浏览器访问 `http://localhost`
- 首次启动自动执行：建库 SQL → 种子数据（角色/管理员/审批流模板）
- 提供 **dev / local-prod 两套 compose profile**，一条命令切换
- 全部容器运行占用约 2–3GB 内存

### 3.3 本机配置要求

| 项目 | 最低 | 推荐 |
|---|---|---|
| CPU | 4 核 | 6 核+ |
| 内存 | 8GB（分 Docker 4–5GB） | **16GB**（分 Docker 6–8GB） |
| 磁盘 | 20GB 可用 | 50GB（MinIO 文件持续增长） |
| 系统 | macOS / Windows(WSL2) / Linux | macOS |
| 需安装软件 | **Docker Desktop**（内存配额调至 6GB+）、**Git** | — |

> Python 3.12 / Node 20 无需装在本机，构建在镜像内完成；仅本地调试代码时才需要。

### 3.4 生产环境（第 6 阶段上云）

- 应用：2×4核8G（K8s 双副本）
- 数据：云 RDS PostgreSQL 15 + 云 Redis + OSS 对象存储 + 云消息队列
- 网络：**弹性公网 IP（EIP，固定 IP）** + 域名 + HTTPS
- 运维：Prometheus + Grafana 监控、日志采集、定时备份
- 预估云成本：约 1500–3000 元/月

## 4. 外部依赖清单（含本地可行性结论）

| 功能 | 依赖 | 本地 Docker 能否用 | 方案 |
|---|---|---|---|
| 四端全部业务功能 | 无外部依赖 | ✅ 100% | 建档/审批/建仓/库存/货架/订单/三种模式/核销/平仓/对账/看板 |
| IoT 视频监控 | 摄像头 RTSP/GB28181 | ✅ | 本地用测试摄像头或模拟流 |
| 实名认证/证照 OCR | 阿里云/腾讯云 API | ✅ | 主动调用型，本地直调，只需开通账号 |
| 短信通知 | 云短信 API | ✅ | 同上 |
| 电子合同 | e签宝/法大大 SaaS | ✅ 基本可用 | 沙箱本地可调；签署链接直达签署人手机 |
| 电子发票 | 百望/航信 SaaS | ✅ 基本可用 | 同上 |
| 运满满/GPS | 对方开放接口 | ✅ 基本可用 | 主动调用型，取决于对方开账号速度 |
| **在线支付收款** | 微信/支付宝 | ⚠️ 半可用 | 拉起支付可以；**异步回调需公网地址**，本地收不到 |
| **银企直联** | 银行核心系统 | ❌ 不行 | 固定 IP 白名单 + 企业签约 + 证书，只能上云 |

### 4.1 支付的三种本地解法

1. **模拟支付通道**（开发期主用）：Mock 支付页点"付款成功"，效果等同真回调，业务全流程可走通
2. **内网穿透**（测真实支付时）：ngrok / cpolar 提供临时公网域名指向本地，微信回调可进来
3. **主动查单**（兜底）：支付后系统定时向微信/支付宝查单确认到账，不依赖回调

### 4.2 银企直联专项说明

- 银行直联要求：企业主体与开户行签约、**报备固定公网 IP 白名单**、数字证书/可能要求 U盾或专线 VPN
- 家庭宽带 IP 动态且常为共享内网 IP，无法满足；云服务器申请弹性公网 IP（几元/月）即可
- **商务周期 1–3 个月，项目第 1 周即启动洽谈**
- 代码设计：`BankAdapter` 适配器接口，`MockBankAdapter`（人工转账 + 回单上传兜底）与真实银行 Adapter 可热切换，业务代码零改动

### 4.3 总设计原则

> **所有第三方依赖均走适配器接口 + 人工兜底实现。** 任何一家接口未到位，平台都能完整跑业务，仅相应环节从"自动"降级为"人工确认"，接口到位后热切换。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 字段级需求确认慢 | 总工期延长 | 清单化确认；超时按默认实现并标注 |

| 银企直联商务周期长 | 自动付款延期 | 第 1 周启动洽谈；人工兜底先行；适配器热切换 |

| 业务规则中途变更 | 返工 | 状态机与审批流配置化设计，改规则多数不改代码 |
